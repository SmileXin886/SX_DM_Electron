
问题一：Request 嗅探用错了 ID 作为 key
你的 Request 嗅探正则：

const submitRegex = /"submit_id"\s*:\s*"([^"]+)"/g;
但 Agent 模式的请求体里根本没有 submit_id 字段。Agent 请求体结构是：

{
  "messages": [
    {
      "id": "475ec02e-f44e-896d-e165-1f37bb3d9332",   ← 这个是 userMessageId
      "content": { "content_parts": [{ "text": "一个小鸟一张照片" }] }
    }
  ]
}
所以你的正则 "submit_id" 匹配到的是 null，但因为你的正则写的是全局匹配，它可能匹配到了请求体里其他地方的 submit_id，或者匹配失败什么都不做。

更关键的是——即使从 Request 中解析到了 userMessageId，你也没有把它存进 rentTaskPool，你只是用 submitId（其实是空或错的）作为 key 存了任务信息。然后等 History 返回真正的 submit_id 时，key 不对，自然就匹配不上。

问题二：History 解析没有提取 metrics_extra
你的 History 解析代码里：

const taskInfo = {
    submit_id: realSubmitId,
    prompt: task.history_group_key || '智能体生成任务',
    billingId: task.model_info?.model_req_key || 'auto_catch',
    ...
    // ❌ 没有提取 metrics_extra.userMessageId
};
而 metrics_extra 里就有 userMessageId：

"metrics_extra": "{\"userMessageId\":\"475ec02e-f44e-896d-e165-1f37bb3d9332\",...}"
你不解析它，自然抓不到。

根因总结
Request 发出时
  → 你的代码没有从 Agent 请求体中提取 userMessageId
  → 也没有建立 userMessageId → requestId 的映射
        ↓
History 返回时
  → 你没有从 metrics_extra 中提取 userMessageId
  → 无法和 Request 阶段关联
        ↓
积分历史到达时
  → 用 submit_id 查 rentTaskPool
  → submit_id 对应的 key 是 Request 阶段的错误 key（或不存在）
  → 匹配失败 ❌
方案
第一刀：Request 嗅探中，专门为 Agent 模式的请求单独处理：

判断 URL 包含 /creation_agent/v2/conversation
从请求体中提取 messages[0].id（即 userMessageId）和 conversation_id
不要用 submit_id 作为 key，改为用 userMessageId 作为 key 存入 rentTaskPool，value 里记录 submit_id = 待填充
同时维护一个 Map<userMessageId, meta> 的映射表
第二刀：History 解析中，提取 metrics_extra.userMessageId：

对每个 task，解析 JSON.parse(task.metrics_extra)
取出 userMessageId、prompt、conversationId
用 userMessageId 找到 Request 阶段存的映射，把真正的 submit_id 填进去
也把 submit_id 作为 key 存入 rentTaskPool
第三刀：积分历史结算时，双重查找：

先用 submit_id 直接查 rentTaskPool
如果找不到，再用 userMessageId 查映射表找到 submit_id，再查
两次都找不到才判定为 alien_task
本质问题就一个：Request 阶段你根本没有正确提取和存储 userMessageId，History 阶段也没有从 metrics_extra 里提取它，两头都断了，所以中间永远连不上。
